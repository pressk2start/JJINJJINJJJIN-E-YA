## 왜 REST 폴링을 버리고 WebSocket으로 갔나

`ob_recorder.py`(REST)는 사이클마다 `오더북 스냅샷 → 종목별 체결 조회`를 돈다.
20종목이면 사이클당 21콜이고, 이 컨테이너 실측 사이클 주기는 6.4초였다.
그 결과 **OBI와 체결흐름이 같은 시점의 시장 상태가 아니게 된다.**
스켈핑에서 2~6초 어긋남은 측정하려는 현상보다 오차가 크다.

WebSocket은 orderbook과 trade가 같은 연결로 각자의 발생 시각을 달고 들어온다.
event-time으로 정렬하면 OBI(t) · microprice(t) · signed flow(t−1s:t)를 실제로 맞출 수 있다.

**실측 (2026-08-23, 상위 20종목):**

| 항목 | 값 |
|---|---|
| orderbook | 73.1건/s (종목당 3.7/s, 갱신간격 p50 **100ms**) · 30호가 · 평균 2,892B |
| trade | 17.2건/s · 평균 457B · **best_bid/ask를 함께 실어 보냄** |
| 용량 | 원본 214KB/s → depth 15 + gzip **12.0x** → **0.88GB/일** (3주 ≈ 19GB) |
| **수신지연** (recv − exchange_ts) | p10 82 / **p50 88** / p90 95 ms (이 컨테이너) |

마지막 줄이 중요하다. 지금까지 왕복비용의 latency 성분(편도 3bp)은 **실측 전 가정치**였다.
레코더가 `recv_ts − timestamp`를 남기므로 이제 **측정 대상**이 된다.
한국 VPS에서는 이 값이 크게 줄어들 것이고, 그만큼 비용 가정도 다시 잡아야 한다.

trade 이벤트가 `best_bid_price/size`·`best_ask_price/size`를 함께 싣는 것도 실측으로 확인했다.
체결 시점의 스프레드·microprice를 별도 조인 없이 정확히 복원할 수 있다는 뜻이다.

### 레코더가 지키는 것

1. **원자료 불변** — 수신 JSON 그대로 + `recv_ts`만 덧붙임. 특징량은 전부 후처리.
   지금 집계해 저장하면 나중에 다른 정의로 다시 못 만든다. 오더북은 소급 불가다.
2. **손실 구간 명시** — connect/disconnect/recv_timeout/heartbeat/shutdown을 `_meta`로
   같은 스트림에 기록. 후처리는 이 구간을 반드시 제외해야 한다.
3. **두 시각 보존** — 거래소 `timestamp` + 로컬 `recv_ts`.
4. **절단을 숨기지 않음** — `units_total`(원래 30)을 함께 기록. depth로 자른 사실이 데이터에 남는다.
5. **주문 코드 없음** — 읽기 전용 공개 스트림. 인증·API 키 일절 없음.


## 비용은 전 종목 공통이 아니다 (2026-08-23 실측)

`GET /v1/orderbook/instruments` 가 종목별 `tick_size` 를 **공식 제공**한다
(2025-07-31 추가). 체결가에서 역추정할 필요가 없고, 역추정은 실제로 틀린다 —
병렬 세션이 그 방식으로 KRW-DOGE 를 0.1원(9.4bp)으로 측정했으나 공식값은 **1원(80bp)** 이다.

관측 스프레드는 대부분 **정확히 1틱**이었다. 따라서 종목별 비용 하한은

    cost_floor_bp ≈ 수수료 왕복 10bp + max(관측 스프레드, tick_bp)

이다.

### ⚠ 아래 표는 counterfactual 이지 과거 재현이 아니다

아래는 **현재** tick_size 로 계산한 cost_floor 를 **과거 88.9일** 수익률 분포에 대입한 값이다.
tick_size 는 가격 구간에 따라 바뀌므로 과거 구간의 실제 비용 구조와 다를 수 있다.
실측 반증: **KRW-DOGE 는 90일 창의 17.1%(2026-07-29~08-19) 동안 100원 미만**이었고,
그 구간의 실제 tick 은 0.1원 = 현재(1원)의 1/10 이다. DOGE 행의 92bp 는 그 기간에 적용되지 않는다.

즉 이 표의 정확한 해석은 **"현재 비용구조를 과거 가격변동 분포에 대입하면 어떻게 보이나"** 이고,
"90일 실거래를 재현하면 이랬다"가 아니다. 역추정을 폐기한 이유(틱이 시간에 따라 변한다)가
여기에도 그대로 적용된다.

→ **용도 분리**: (A) 현재 거래가능성 screening 은 현재 tick 으로 맞다.
  (B) 과거 구간의 execution cost 재현은 하지 않는다 — 당시 tick policy 를 복원하지 않을 거라면
  90일 결과는 **signal discovery 용으로만** 두고, 정확한 비용은 WS forward 구간부터 붙인다.

(29종목, h=5분):

| 종목 | tick_bp | cost_floor | 공통가정 → 종목별 |
|---|---|---|---|
| KRW-TRUMP | 2.96 | 13.0 | 18.9% → **27.9%** (+9.1%p) |
| KRW-ETH | 3.06 | 13.1 | 5.3% → 10.9% (+5.6%p) |
| KRW-XRP | 5.06 | 15.1 | 5.9% → 9.9% (+4.1%p) |
| … | | | |
| KRW-XLM | 38.61 | 48.7 | 28.0% → **6.9%** (−21.0%p) |
| KRW-RVN | 28.74 | 95.8 | 25.8% → 2.9% (−22.9%p) |
| KRW-MOVE | 94.34 | 104.3 | 24.9% → 3.0% (−21.9%p) |

29종목 중앙 cost_floor 는 **30.6bp** — 공통 가정(21.7bp)보다 높다.
⚠ cost_floor 는 이름 그대로 **하한**이다. 실제 비용에는 book walk·market impact·지연 역행이 더 붙는다.
⚠ 높은 tick_bp 는 "거래 불가"가 아니라 **"요구 알파가 매우 높다"** 는 뜻이다.
   구조적 불가라고 부르려면 "최소 체결비용 > 검증된 조건부 엣지의 상한"이 함께 성립해야 하는데,
   그 상한은 아직 모른다. 현재 판정은 "연구 유니버스에서 제외하는 것이 합리적"까지다.
cost_floor ≤20bp 10종목은 **과소평가**되고 있었고, >40bp 10종목은 **과대평가**되고 있었다.
반전 가짜신호가 몰렸던 DOGE 는 실제 비용 바닥이 92bp 로, 공통 가정의 4배다.

⚠ 스프레드는 1회 스냅샷이라 노이즈가 있다 (BTC floor 가 두 실행에서 10.1 ↔ 15.5 로 움직였다).
   WS 레코더가 쌓이면 스냅샷이 아니라 **분포**로 대체해야 한다.


## 후처리 규약 — event-time 재생 (`ws_features.py`)

수집은 원자료만 남기고 특징량은 후처리에서 만든다. 그 후처리가 지켜야 하는 것 네 가지.
전부 실제로 발생했던 버그 유형이고, `tests_ws.py` 6스위트가 합성 이벤트로 강제한다.

**1. emit 먼저, apply 나중.** 이벤트를 상태에 반영한 뒤 과거 grid 를 내보내면
미래 정보가 과거 frame 에 새어든다. 이벤트 간격이 5초면 그 하나가 그 사이 모든
1초 frame 에 역으로 들어간다. 경계 규약: **event_ts ≤ grid_ts 인 이벤트만 그 frame 에 포함.**

**2. 연구 시계는 거래소 시각이다.** `recv_ts` 로 정렬하면 네트워크 jitter 가 시장 순서를 바꾼다
(거래소 OB→trade 인데 수신은 trade→OB). primary clock:
orderbook `timestamp` / trade `trade_timestamp`(체결시각, `timestamp` 와 실측 49ms 차이).
동률은 `_seq`(수신 순번)로 결정적 정렬. `recv_ts` 는 latency/QC 전용.
유한 버퍼 재생이므로 `lateness_ms` 를 넘는 역순은 **검출해서 폐기 카운트**한다 — 조용히 반영하지 않는다.

**3. depletion 은 가격별로 매칭한다.** 감소를 통째로 누적하고 현재 best price 의 체결만 빼면,
호가가 100→99→100 으로 움직인 구간의 감소가 설명되지 못해 비율이 1 로 편향된다.
`Σ max(depl[p] − exec[p], 0)` 으로 가격별 매칭한다.
그리고 **관측 창 밖으로 밀려난 레벨은 세지 않는다** — 스냅샷은 상위 N단뿐이라
창을 벗어난 잔량은 사라진 게 아니라 안 보이는 것이다.

**4. 상계는 스냅샷 transition 안에서 끝낸다.** 프레임 전체로 감소와 체결을 각각 뭉쳐서
마지막에 상계하면 **앞선 체결이 나중 감소를 설명해버린다**:

```
0.10s  bid 100 = 50
0.20s  100 에서 매도체결 20
0.30s  bid 100 = 50      ← 즉시 재보충. 순감소 없음
0.80s  bid 100 = 30      ← 이후 취소 20
1.00s  frame             ← 뭉쳐서 상계하면 depl 20 / exec 20 → unexplained 0 (틀림)
```
정답은 20이다. 그 체결은 이미 재보충으로 흡수됐고 나중 감소는 체결과 무관하다.
→ 각 transition `(prev_ob_ts, cur_ob_ts]` 마다 그 구간의 같은 가격 체결로만 상계하고,
프레임에는 **이미 상계된 결과만** 누적한다.

**5. 낡은 호가로 프레임을 찍지 않는다.** 격자는 이벤트가 올 때마다 이전 grid 를 채우는데,
재접속·수집 중단·한산 구간에서는 **같은 스냅샷의 복사본**이 초당 하나씩 계속 나온다.
실측: 두 스모크 세션 사이 공백 때문에 61,985 프레임 중 **96%가 낡은 복사본**이었고
book_age 중앙값이 2.6시간이었다. 표본 수가 허구로 부풀고 자기상관이 극단적으로 커진다.
→ `--max-stale-sec`(기본 60초) 초과 프레임은 만들지 않고 카운트만 한다.
적용 후 book_age_ms p50 이 9,527,716 → **316** 으로 정상화됐다.

**6. 이름을 정확히 쓴다.** `cancel_ratio` 가 아니라 **`unexplained_depl_ratio`** 다.
스냅샷만으로는 취소와 중간 replenishment 를 식별할 수 없다.

### 실측 (스모크 · 20종목 · transition 귀속 + 신선도 상한 적용 후)

| 집계 범위 | p25 | p50 | p75 | n |
|---|---|---|---|---|
| 전 호가단 | 0.999 | 1.000 | 1.000 | 1,325 |
| **최우선호가만** | **0.000** | **0.919** | 1.000 | 641 |

전 호가단 값은 깊은 단의 일상적 갱신 때문에 **구조적으로 1 에 붙는다** — 정보가 없다.
최우선호가만 보면 분포가 살아난다 (프레임의 1/4 이상에서 touch 감소가 체결로 완전히 설명됨).
병렬 세션이 관측한 "cancel_ratio 중앙값 1.00"은 전 단 합산 + 가격별 미매칭이 만든 축퇴였다.
**벽의 진위는 최우선호가 기준으로만 판단한다.**

⚠ 라벨(`fwd_*_bp`)의 기준가는 **mid** 다 — 진입 가능한 가격이 아니다.
체결가 가정은 비용모델에서 따로 적용한다. 둘을 섞으면 신호가 없는 건지 비용이 큰 건지 구분할 수 없다.


## WS 구독 파라미터 — depth 와 level 은 다른 것이다 (실측)

| 구분 | 뜻 |
|---|---|
| **depth** | 몇 호가를 받/저장하느냐 (개수) |
| **level** | 거래소가 호가를 **묶어서** 보내느냐 (가격 집계 단위) |

구독 코드에 `.{n}` 을 붙였을 때의 실제 동작을 확인했다:

| 구독 코드 | level | units | 매수호가 간격 |
|---|---|---|---|
| `KRW-BTC` | 0 | 30 | 1000, 2000, 3000… |
| `KRW-BTC.15` | 0 | **15** | 1000, 2000, 3000… |
| `KRW-BTC.5` | 0 | **5** | 1000, 4000, 6000… |
| `KRW-BTC.100000` | 0 | 30 | 1000, 2000… (범위 밖 → 무시) |

→ `.{n}` 은 **개수 상한**이고 묶음이 아니다. `level` 은 모든 경우 0 으로 유지되며
가격 간격도 tick 그대로다. 즉 호가가 뭉개지지는 않지만 **개수는 영구히 잘린다.**

`ws_recorder.py` 는 접미사를 쓰지 않고 평문 코드로 구독하므로 **level=0 · 30단**을 받는다.
연구 원자료로는 이게 가장 깨끗하다: **level 0 · 무절단(--depth 0, 기본값).**
